# `raid-walk` flags

Usage: `turtle-agent raid-walk <plan> [--server <server>] [--slot N] ...` or `turtle-agent raid-walk report <dir> ...`. A leading plan moves past the flags before parsing, so flags-first callers parse as before. On/off flags (`--place`, `--decisions`, `--allow-split-ledger`) take `=`: `--flag=off` turns one off, and a bare flag means on.[^walk-cmd]

## Identity and inputs

| Flag | Default | What it does | Example |
|---|---|---|---|
| `--server` | none: always pass it | The slot server. Pass `--server <server>` on every run: the built-in default is a test server name, so always set it. | `--server <server>` |
| `--slot` | any free slot | The slot id. `3` is refused before anything (owner rule, exit 15). | `--slot 2` |
| `--holder` | `raid-walk-<plan>` | The lease holder (1-64 letters, digits, `.` `_` `-`). Two equal holders in the pair form are refused. | `--holder <holder>` |
| `--dir` | `dungeons` | The folder of plan files; the plan JSON is `<dir>/<plan>.json`. | `--dir <plans-dir>` |
| `--sql` | none | The deployed migration: step numbers and the first point come from it. Required with `--place` and with `--until boss-done` on mismatched exports. | `--sql <world-sql>` |
| `--out` | `./raid-walk-<plan>-<stamp>` | The output dir, refused if it exists. Mode 0700, files 0600. | `--out <walk-dir>` |
| `--binary` | this executable | The agent binary slot setup copies. | `--binary ./turtle-agent` |
| `--mmaps` | none | The navmesh dir for slot setup. | `--mmaps <nav-dir>` |
| `--slots` | slots file | The slots file. `--allow-split-ledger=on` permits a file outside the default dir (test sandboxes only). | `--slots <file>` |

## Where the run goes

| Flag | Default | What it does | Example |
|---|---|---|---|
| `--until` | `boss` | `boss` stops before the first boss step, `boss-done` after it, `none` is a full clear, `step N` or `leg L` stop there. | `--until boss-done` |
| `--from` | none | `"leg L"` or `"step N"` for the run leader; only for a raid already standing there, unless `--place` stages it. | `--from "leg <leg>"` |
| `--place` | off | With `--from`: put the raid at that start inside the instance. Test servers only, needs `--sql`, refused with `--inject`. Bare `--place` is on; `--place=off` turns it off. A same-instance try that finds half the hires dead or the start leg's boss fighting the party ends the placement at once with exit 29 (`place: party dead ...` / `place: boss engaged with the party ...: fresh instance needed`), where the autopilot relaunches a fresh instance instead of feeding the boss. | `--from "leg <leg>" --place` |
| `--no-place-unfreeze` | off | With `--place`: turn off the unfreeze check. The `spread=5` place can drop two seats onto a small disconnected navmesh island beside the place point, where every move fails; by default, from the first watch poll after each placement move (the `.tt place`: 11 yd ring; every GM summon wave of a retry, a retreat or the reuse/bind gather: 6 yd ring at its own point; a re-arm first writes the running check's summary) and for 120 s, sampled once per poll, a hire that is alive, in the instance, not the main tank, has stood still (under 2 yd for 10 s) within the ring of the placement point and more than 35 yd from the main tank while the main tank is more than 15 yd from the point is put onto the main tank (the commander `.go xyz` onto him at z + 2, waits up to 5 s for the landing within 5 yd, then `.summon <hire>`; the commander stays there, possibly in the fight), at most twice per hire. Combat is not part of the rule. A successful summon writes `placement: re-placed <hire> (frozen at x,y,z for <s>s)` to run.log; a failed one `placement: re-place failed <hire> (<reason>)` (at most 3 per hire, 5 s apart). Three failed `.go` moves in a row (no landing counts as one), the main tank's death or a wipe stop the check (`placement: unfreeze check stopped (<reason>)`), and it ends with `placement: frozen=<n> re-placed=<n>`. | `--place --no-place-unfreeze` |
| `--reuse-instance` | off | With `--place`: keep the raid's current instance (no fresh entry, no cap count). Combines with `--gm-clear`. The kept copy and the resumed bind are quiet-checked after the GM clear and before the first `.summon`. Before either path places, every boss arena is read (`q units 60` around each plan boss row within 150 yd of the landing, and around each boss-hold row — a boss fought on the spot has no boss row; its hold row's spot is the arena and its first entry the boss — `cb` the combat state): a boss or arena unit still fighting from a dead attempt (walk 97 fight 9-1, exit 18 mid-fight) gets no placement, the walk waits up to 90 s for the reset, and a fight that does not reset exits 29 (`place: --reuse-instance: ... fresh instance needed, no placement into a live boss fight`) so the autopilot's fresh-instance retry takes over. The arenas are read again as the final gate immediately before the first `.summon`, after the GM clear and the quiet: a fight that began meanwhile exits 29 at once with the same reason (the final gate never waits, since a patrol can walk into the landing during a wait). | `--place --reuse-instance` |
| `--speed` | `1.0` | The run's test speed, 1.0 to 3.0 with one decimal. Above 1.0 sends `speed=X` and marks a test run. | `--speed 3.0` |
| `--enter` | `auto` | `auto` tries `near` and falls back to `tele` once on `requirement`; `tele` needs the plan's `entrance_tele`. | `--enter tele` |
| `--max-run-minutes` | `90` | The ceiling from `run start` to the end. The lease lasts max-run plus hold plus 30 (limit 720). | `--max-run-minutes 120` |
| `--hold-minutes` | `0` | Keep the raid bound this many minutes after the run. | `--hold-minutes 5` |

## Hires and tier

| Flag | Default | What it does | Example |
|---|---|---|---|
| `--hires` | from the plan | The tb-raid-roster file (v1 or v2); without it the roster comes from the plan's `raid {size, tanks, healers, dps}` block. | `--hires <roster>` |
| `--tier` | `0` | The hire gear tier (1-3) of a raid the committed table leaves unknown. | `--tier 1` |
| `--tier-override` | `0` | The hire gear tier (1-3) in place of the raid's minimum: a comparison, not a tier proof. | `--tier-override 3` |
| `--hire-settle` | `20s` | The ceiling of the wait after the last hire for its join summons before the refit and the bind; the wait is a poll of the group and ends as soon as every hire has joined (in the group list and online). `0` skips the wait. Below the default marks the summary `settle_short`. Walk 12's last join came 4-8 s after the hire answer, and 20 s covers a 15 s late join with margin; walk 74 paid the old flat 20 s on every attempt. | `--hire-settle 30s` |

The refit is `.bot gear raid <commander> tier <N>`. The module's gear queue is one slot for the whole server, and a job's verdict goes only to the character that queued it; neither the verdict nor the `TBM:ACTION_ERR|gear|busy|...` refusal carries a job id or a requester id (the verdict names status, bot counts, tier, cap, average item levels, capped slots, skipped bots and purged items). A refused refit therefore cannot say whose job holds the slot, so the walk gives it the same 1m bound it gives a gear job of its own: a `TBM:GEAR` verdict for the refit's tier inside that window is the slot's job answering this commander (an earlier attempt's own refit, a walk restarted while it ran), and it is used as the refit's verdict with no re-send; a verdict for another tier answers another request and is dropped. A window that ends with no verdict means the slot's job is another requester's, whose verdict never reaches this chat, and only then is the line re-sent. `gearBusyBudget` (2m: one window for the slot's job and one for the re-send's verdict) bounds the whole wait; a slot still busy then ends the walk 18 on the module's own line. Limit: the window's last poll and the re-send are separate calls, so a verdict the slot's job writes between them can still be read as the re-send's; it is a same-tier verdict of this commander's own job, so the walk ends on a refit it asked for, but the re-send may still be running. With no job or requester id in the reply, no client can close that window.

## Test-server tools

| Flag | Default | What it does | Example |
|---|---|---|---|
| `--gm-clear` | none | Repeatable: `"<leg>:<group>[,<group>...]"` — GM-kill those pull groups after the placement. Needs `--place`; the walk is then ASSISTED. | `--gm-clear "<leg>:1,2"` |
| `--gm-clear-boss` | none | Repeatable: `<leg>` — GM-kill the leg's boss and its pack. Needs `--place`. | `--gm-clear-boss <leg>` |
| `--gm-clear-spawns` | pack default | The world export dir the clears read the packs from. | `--gm-clear-spawns <dir>` |
| `--gm-instance-data` | none | Repeatable: `"<leg>:<a> <b>[;<a> <b>...]"` — send each as `.debug instancedata` when the walk first starts the leg, 0.5 s apart after each line's 2 s reply window. Test servers only. Every launch sends the lines after placement, `--reuse-instance` restarts included (one walk never sends a leg twice), and that includes a launch that resumes from `--from step N --place --reuse-instance` (the autopilot's restart), pinned by `TestGMInstanceDataReuseResumeFromStepSendsOnceBeforeRunStart`. The instance data can be lost between launches: the zulgurub boss scripts overwrite their own slot on Reset (`boss_jeklik.cpp:105-106` sets `FAIL` on a living Jeklik, `boss_venoxis.cpp:152-153` sets `NOT_STARTED`, both without a DONE guard; Hakkar then casts that priest's Aspect, `boss_hakkar.cpp:228-240`). Walk 44, raid hk7m attempt -3, a `--reuse-instance` restart that sent nothing, saw exactly that. A wipe recovered in place inside one running walk may keep the data, so the walk clears its markers on every wipe recovery and the next status that names the leg resends the lines under their own pause and resume; the resend is idempotent, so both cases are safe. A GM `.die` kill does not stop the respawn, and a respawned priest's Reset() overwrites its data again, so after `run start` the walk sends the lines (first send of a leg, wipe-recovery resend, or the once-per-boss-row resend) ONLY at an allowlisted status: phase `rest` or `gather` that passes the pre-pull gate (no pulling or fighting note, no later pull line in the same event page, no bot of the party in combat in a frame under 15 s old), under the usual pause and resume. The only other send is the launch send before `run start`. At any other status (walking, begin, pull, fight, hold, boss rows, unknown phases) a pending send is deferred and never fires, because a pause there can land mid-pull (the boss row becomes current about 1 s before the run can pull, and a mid-fight pause drops the focus for ~7 s). The once-per-boss-row resend goes out at the rest/gather of the step before the boss row (walk 45 hk7m: a GM `.die` kill does not stop the respawn, and a respawned priest's Reset() overwrites its DONE data); a deferred send whose leg never produces a qualifying rest/gather (the walk leaves the leg, or the run ends inside it) is reported, not dropped silently: a summary note and a run.log WARN `gm-instance-data: <leg> lines NOT sent (no out-of-combat rest/gather in the leg)`, counted as `gm_instance_data_unsent` in the summary (the walk does not fail); a boss row that becomes current with no such rest logs `gm-instance-data: no out-of-combat rest before boss row N; resend skipped`. The `Initialize()` memset (`instance_zulgurub.cpp:38`) only runs when an instance is created. | `--gm-instance-data "<leg>:1 3"` |
| `--prepull-aura` | none | Repeatable, one value per role: `role=<tank|melee|ranged|caster|healer|all>:<id,id,...|preset>`, or a `tb-prepull-auras` file that names the roles at once (one list per role under `roles`, `dungeons/prepull/zg-preraid.json`). A role named twice, by two values or by a file and a value, is refused. At the step before EACH boss row, WHATEVER its phase (walk 101b: the ZG Thekal plan's step before boss row 255 is a plain move, so a rest/gather-only gate never fired), while the run is still before the pull (no pulling/fighting note, no later pull line of the page, no party bot in combat), the walk pauses the run, puts each living raid bot's lists on it with a GM select-then-`.aura <id>` (the `buffs.go` kernel: the first aura checked, one retry, an aura that lands on the commander is a miss), reads them back and resumes. The targets are the walk's own hires, matched by name in the commander's raid read from its view (`bot_view`): the walk's own `party` RPC is the PLAYER's group, and the hired bots raid without the player, so walk 101's fire saw 0 bots and still wrote boss row 691. A frame member the walk never hired is logged and watched for combat (an in-combat or unreadable row stops the batch) but never targeted, and a hire whose aura role the walk cannot tell fails the fire before any aura: no class in its unit row, a bot the module's `.bot roster` state snapshot leaves out, or a state row whose kit names no spec or specs of more than one role (only the `all` lists would otherwise reach it while coverage passed). Every bot the walk hired must receive a list: a fire that reaches none of them, or fewer than the roster (a bot missing from the view, a dead bot, a role word no class produces and no `all` list), fails with the bots and reasons named, no aura sent to the rest. A run that passed that step too fast to pause is paused on the boss row itself, and only before the pull (no member in combat and the boss's arena read FRESH from the server, `q units 60` around the row with `cb` the combat state — never the cached hostile frames, which can still show a pulled boss unengaged; an engaged boss, a read that fails, is truncated or lists a unit without a well-formed `cb` (an unknown combat state counts as in combat), or a pause past the row fails the walk). The pause is fail-closed: a refused or unconfirmed pause sends no aura, the commander and every living raid member (list or no list) are re-read for combat right before the first `.aura` and before every later one (the view leaves the player out, so its own `unit` row is read too), an in-combat unit or an unreadable `unit` row stops the batch and fails the walk, and a boss row that becomes current without a verified fire fails the walk instead of counting as handled. The auras a member already carries are skipped, so a later boss row only tops up what a death or a buff strip took. `all` applies to every living member. Every other role comes PER BOT from the module's own state rows (`raidwalk.BotStateAuraRole`), not from the class and not from the roster batch: the walk reads `.bot roster`, whose `TBM:BOTSTATE|<bot>|...specs=<strategy>+<strategy>` field is the spec kit the module installed on that bot (holy/restoration/discipline `healer`; protection/tank feral/tank shaman `tank`; retribution/dps feral/enhancement `melee`; hunter `ranged`; shadow/balance/elemental/mage/warlock `caster`; the `offdps` switch is skipped). The mt/ot stay `tank` whatever their kit, but they need a state row like every hire. A mixed batch like walk 101b's `5h 13d` is no obstacle: it names no role for a priest, paladin, druid or shaman, while each bot's row names its own spec. A bot with no row, an incomplete snapshot (the BEGIN count must match the rows), a kit naming no spec, or a kit naming specs of more than one role fails the fire for that bot: the walk does not guess. `prepull-auras.json` records the source as `role_source` and each bot's `specs`. `world` is the `world-raid` preset (Rallying Cry 22888, Songflower 15366, Spirit of Zandalar 24425, Fengus/Mol'dar/Slip'kik 22817/22818/22820 — Warchief's Blessing 16609 is Horde-only and left out); every other preset is `dungeon.BuffPresets`. (A world buff is stripped when a player ENTERS a map that lists it, map 309 among them, `instance_buff_removal` + `AuraRemovalMgr::PlayerEnterMap` from `Map::Add`; the lists go on inside the instance, so they hold, and a wipe that leaves and re-enters is refired by the recovery.) `prepull-auras.json` in the out dir records the flag, the tolerance, the merged lists, the boss rows whose fire verified and each bot's ids sent/seen/missing; it is written on every fire, failures included, so the missing list is always on disk. A fire that failed never appears in `boss_rows`: it is a separate `attempts` entry (`{boss_row, reason}`), so a consumer can tell a verified preparation from a failed one. Every requested aura must verify by default; `--prepull-aura-tolerance N` accepts up to N misses per bot. Test servers only (`gm_aura`, the same gate as `gm_kill`). | `--prepull-aura role=tank:17626,17538 --prepull-aura all:world,23768`, `--prepull-aura dungeons/prepull/zg-preraid.json` |
| `--prepull-aura-tolerance` | `0` | The most auras one bot may miss after a fire, needs `--prepull-aura`. `0` (the default) requires every requested aura to verify; a bot over the bound fails the walk (exit 18). The missing list goes to `prepull-auras.json` either way, and a tolerated miss is logged as such, never as every bot carrying its list. | `--prepull-aura-tolerance 1` |
| `--prepull-aura-when` | `boss` | `boss` (the default) is the per-boss-row fire above. `start` fires the same lists ONCE, after the hire, the gear and the placement and before `run start`, so the run's first move already carries them (a flask and the world buffs last 2 h or more); the run is not running, so no pause is needed, and the fire goes out only on a positively confirmed idle run: a parsed `TBM:RUN` line in state `none` or `done`; a refused answer, an answer without that line, a paused run, and any running state whatever its plan all send nothing and fail the walk (walk 101: a bot entered combat at Hakkar's row 689 during the boss-row fire's ~120 sends, 4 of 4 attempts). Every coverage rule and the tolerance hold; the verified fire is `start_row` in `prepull-auras.json` (never a boss row), and a failed start fire is an `attempts{start:true, reason}` entry. The start fire first waits up to 60 s (2 s polls) for every hire to be in the commander's view and alive and in the agent's unit store, because it goes out inside the placement's teleport wave (walk 101: the ZG Jeklik run at plan start row 1 stopped 0.16 s after the last `.tele` on `the unit read of <MT> failed twice`); a hire still missing after the wait fails the walk, and `run.log` names how long the wait took. In this mode a boss row sends nothing: at each boss pull (the boss row current in the plan's `pull` or `task`/fight-start phase, never the step before it) the walk only READS which auras each hire still carries and logs them, reading the row at the pull and refreshing it once at the fight start, and recording the phase only after a successful read so a failed read is retried at the next qualifying status (`prepull-aura: boss row N: X of Y hire(s) carry every requested aura at the pull: <bot> <have>/<want>[ (missing ids)]; ...`), so the run.log shows the coverage the fight started with. | `--prepull-aura-when start` |

## Practice runs

`--practice <entry>` keeps one boss fight alive for mechanic practice on a test server: the run walks to and pulls the boss as usual, then the walk collects the mechanic's cycles, revives the raid and restores the boss between attempts, and resets the boss with GM tools instead of losing the raid after two or three cycles. It needs `--place` and `--from` (it starts the raid at its boss row) and is refused on every server outside the test pair, at option parse and again before every GM action. The walk is marked **PRACTICE ASSISTED**, and it never credits a boss kill: a boss death during practice ends the practice at once ("boss killed during practice") without a respawn. A `--practice` walk whose boss never engaged still carries `practice{ended: "never engaged"}`, so the summary is always PRACTICE ASSISTED and never carries a `boss_kill`.

| Flag | Default | What it does | Example |
|---|---|---|---|
| `--practice <entry>` | none | The boss's creature entry. `14834` is Hakkar (the mechanic table); any other entry is window mode (see `--practice-window`). Needs `--place` and `--from`; test servers only. | `--practice 14834` |
| `--practice-cycles` | `10` | The mechanic cycles the run collects before it ends. | `--practice-cycles 10` |
| `--practice-max` | `20m` | The practice loop's wall-time ceiling. Reaching it stops the practice with exit 18 (`practice stopped: max time`). | `--practice-max 25m` |
| `--practice-rest` | `30s` | The out-of-combat rest between attempts (restarts if a hire enters combat). | `--practice-rest 45s` |
| `--practice-boss-floor` | `40` | The boss HP percent below which it is restored to its own max: checked on every poll and at every cycle row on the newest reading across every source the walk has (the tracked frames, the newest frame's hostile rows and bot targets, and the commander's own client), but a restore acts only on a fresh (< 3 s) reading with a known HP. The boss counts as gone only when every source has missed it for 30 s, or a source reads it dead (the kill ending); one slow poll, one missing source or an unresolved GM hand is not a despawn. | `--practice-boss-floor 50` |
| `--practice-sustain` | `on` | Revive dead hires and restore the boss at each cycle (`on` or `off`). | `--practice-sustain=off` |
| `--practice-window` | `120s` | The cycle window of an entry the mechanic table does not know: one cycle per window, no spell detection, 3 cycles per attempt, no respawn set. | `--practice-window 90s` |

The mechanic table's timings are the core's own (cited in `internal/raidwalk/practice.go`):

|---|---|---|---|---|---|---|---|---|
| `14834` | Hakkar | Blood Siphon 24324 | 90 s | 90 s | 20 s | 600 s | 5 | Sons 11357 |

Safety rules (binding; each has a test):

1. A practice run only where `gm_kill` is allowed today: the server is in `placeServers` AND the agent's session dialled that server's configured world_addr (its `AllowGMKill`). The walk refuses at option parse and re-checks the server before every GM action.
2. The GM line set is closed: `.die` (the existing gm_kill), `.npc evade`, `.modify hp <n> <n>`, `.respawn` (the selected form only), `.revive <name>`, plus the existing `.debug instancedata`. `session.PracticeGMLine` builds every line; any other text is refused before it reaches the session.
3. Targets: the practice boss's guid is bound ONCE at the practice start, from the engagement frame (the hurt unit of the entry, or the one holding a party target). `.npc evade` and the hp restore name only that guid. When the frames name one engaged unit, exactly that guid binds, and a client unit list that does not hold it fails the practice before any GM action (`practice: ... is not among the client's ...`, ended `boss not bound`); without an engaged unit only a single candidate of the entry binds, and several with no engaged one fail too (`practice: ... cannot tell the boss from the trash`). So a duplicate-entry trash unit is never reset. `.respawn` only on guids of the mechanic's respawn set recorded from the client's unit list at the attempt start (and confirmed dead); `.revive` only for names in the walk's own hire list, plus the commander's own name when the status shows it dead.
4. Bounded: `--practice-max` (default 20 m), at most 4 attempts, 3 failed resets in a row → `practice stopped: <reason>` with exit 18. A reset uses the commander's `run pause` (never `.bot run stop`: a stop ends the run and erases its slot). The pause must be answered by a status that shows this plan paused on this run within 10 s, EXCEPT when the server says the run is not running (paused, done or gone: `no-run` with no slot at all, or `state` with a slot that is not Running; practice 2/3's ~10.5 min incident): the reset then proceeds without a held run. The resume at the end is skipped when the pause found no resumable run (`no-run`, or `state` with a Done or absent run); a Paused run still resumes afterwards. Any other refusal, no ACK, or an ACK without that status ends the practice before any GM action (exit 18, ended `run pause refused`), so the reset never runs under a still-running raid. An attempt after a reset is clocked from its re-engagement: up to 60 s for the boss to fight again (below 100 %, a party target, or the engagement incident). No re-engagement in that wait is a failed reset, counted once per reset (a reset that did not land is not counted twice); the events keep being read after the timer fallback, a cast within EverySec/2 of the last counted one is the same cast, and an already-read events page keeps its unread tail for the next read.
5. Marking: the summary says `PRACTICE` and `ASSISTED`; a practice walk never credits a boss kill and never meets a `boss:` goal; a boss death during practice ends the practice ("boss killed during practice", no respawn of the boss).
6. No DB writes, no config edits, no server restarts, no `.respawn` without a selection, no `.reset`/`.instance` commands.

Each attempt records one row per cycle in `<out>/practice.jsonl`:
`{attempt, cycle, total_cycle, cast_at, detect, alive, dead_since_last, boss_hp_pct, sons_alive, sons_known, sustain:{revived:[...], boss_hp_set}}`.
`detect` is `event` (a `spell_go` of the mechanic's SpellID from the bound boss guid; a `spell_start` is not a cycle, and a duplicate within every/2 is the same cast), `timer` (no cast seen by FirstAtS+10 s, so the boss's own timer is used), or `window` (window mode). The boss HP floor is checked on every poll, not only at the cycle rows, so a boss that dips between rows is restored before the next mechanic; a restore acts only on a fresh (< 3 s) reading with a known HP, and a GM hand the client cannot resolve is noted without counting toward gone. The boss counts as gone only when a source reads it dead (the kill ending) or every source has missed it for 30 s (exit 18, `practice: the boss is gone`); a poll whose event wait ran long, a frame gap or one source dropping the unit is not a despawn. The summary carries
`practice{entry, attempts, cycles, ended, rows, fight_ids}` and `practice: <cycles> cycles in <attempts> attempts, ended: <reason>` in `summary.txt`. `fight_ids` are the dashboard fights that started at or after the practice start, back to 15 s before the bind so the first pull's fight is included (the practice attempts the fight tools skip), and `fights-run.json` of a practice walk carries `"practice": true`. Expected pace for Hakkar: 5 cycles per attempt (~8 min), so 10 cycles are 2 attempts and 2 resets (~17 min).

## GM and toolkit allow-lists

Every GM line passes the allow-list before it is sent; a refused line is a programming error and stops the walk. A practice run's hands are the closed set above (`.npc evade`, `.modify hp <max> <max>`, `.respawn` and `.revive <name>`); they go through the agent's gated RPCs (`gm_evade`, `gm_set_hp`, `gm_respawn`, `gm_revive`), never through the generic `gm` method. `--prepull-aura`'s auras go through `gm_aura` (a player guid and a nonzero spell id; the RPC selects the bot by guid, waits for the server to show that selection and sends `.aura <id>` only while it stands), so auras never ride on whatever the agent had selected. `gm_set_hp` takes the guid only: the session reads the unit's own MaxHealth and sends it for both values, so no caller can lower a unit's maximum. The walk may send: `.gm on` (the place phase's probe) and `.gm visible off` (the revive hides the commander); `.go xyz <x> <y> <z> <map>`; `.pinfo [<hire>]` (the instance ledger's account read; a name must be a hire); `.tele name <hire> <word>`; `.summon <hire>` and `.revive <hire>`; `.appear <hire>` (into the raid's copy); `.instance unbind <plan map>` (that map and no other) and `.instance listbinds`; `.debug instancedata <a> <b>` (the `--gm-instance-data` tool, two integers, nothing else); `.bot hire raid ... level=<n>[ t<tier>]`; `.bot gear raid <commander> tier <N>`; `.bot role <hire> <spec>`; `.bot run stop[ time limit reached (raid-walk <m>m)]` and `.bot run resume`. Nothing else: no `.die`, no `.npc`, no `.kick` through this path (the `--gm-clear` kill goes through the agent's `gm_kill` RPC instead).[^walk-cmd]

Every toolkit line passes its own allow-list too: one line, at most 200 characters, no `#`. The walk may send `q inst`, `q floor <x> <y> <z>`, `q group of=<hire>`, `q units <r<=80> <x> <y> <z> all [dead] [e=<entry>]`, `quiet <r<=50> <x> <y> <z> w=<0..30> dz=<1..15> [skip=<ids>]`, `place <x> <y> <z> spread=<0..8> of=<hire>`, and `clearto <map> <x> <y> <z> <r<=30> dz=<1..15> all=1 [skip=<ids>]` (the map must be the plan's). Never `kill`, `boss`, `force`, `me`, `reset` or `here`; never a `clearto` without `dz=`; never another map; never a name that is not a hire. At most 16 entries ride one `skip=`; a plan whose legs' skip union is longer is refused before any GM line.[^walk-cmd]

## Output files

The out dir holds `run.log` (every phase line with `HH:MM:SS.mmm` stamps), `prepull-auras.json` when `--prepull-aura` is set (the flag, the tolerance, the merged role lists, `boss_rows` — the rows whose fire verified within the tolerance — `start_row` under `--prepull-aura-when start` (the one start fire, verified), `attempts` (`{boss_row, start?, reason}` for the fires that failed, so the two are never confused) and every bot's `{bot, role, specs, sent, seen, missing}` plus the `role_source` (the module's `TBM:BOTSTATE` spec rows), written on every fire, failures included), `commanders-NNNN-<reason>.json`, `combat-fight-*.json` with the full `combat-fight-detail` beside it (the detail stays live while the fight runs), `combat-fights.json` (the dashboard's raw fight list) with `fights-run.json` beside it (`walk_started` plus the sorted `history_ids` the dashboard already listed when the walk began, so an analyser can filter the raw list without `START.epoch`; `history_ids` is the reliable filter and `walk_started` is informational (this raid-walk's own start on the laptop clock). When the pre-placement dashboard read failed, the at-start set falls back to the records' start times: a row counts as history only if it started over 10 s before the walk began), `frames.jsonl` (one frame per 10 s idle, one per 2 s in fight; `power_type` 0-3, 0 omitted; tier recorded), `pulljoiners.json` (one record per pull attempt by pull time: the frames' own count of engaged hostiles outside the pulled pack within 10 s of the pull), `slot-setup.txt`, `teardown.json`, `summary.json` (v1) and `summary.txt`.[^walk-cmd]

A practice walk's `summary.json` carries `practice{entry, attempts, cycles, ended, rows, fight_ids}` and no `boss_kill`/`boss_kills` (practice never credits a kill). Otherwise `summary.json` carries `boss_kill{entry, step, engaged, killed, skipped, phase, phase_entry, evidence}` for the last engaged boss (the run leader's own kill report, the phase the boss unit was seen with, and the evidence or the reason it does not hold), one `boss_kills[]` record per boss step the run's statuses showed, and `teardown{failed, hires_left, reason}` (the first failing step, empty when nothing failed). A dashboard fight record with outcome `kill` for the goal boss's own row credits `boss_kills` even when the run's frames stopped with the fight; a record the dashboard already listed when the walk began (an earlier walk's or instance's) credits only when this walk's frames never showed that boss alive. Each fight in `summary.json` carries `history: true` when the dashboard already listed it before this walk filed one (an earlier walk's or instance's record: kept for the kill credit, with no `combat-fight-<id>.json` copied into this walk's dir). A `--place` walk adds `place{start_step, leg, until_step, instance, circles[], not_cleared[], quiet, placed, hires, summoned[], notes[]}`; a `--gm-clear` walk adds `assisted` and `gm_clear[]`; an `--inject` walk adds `injections[]`, `incidents[]` and `deaths.injected`.[^walk-cmd]

## Exit codes

0 the run ended by its `until` (or the hold). 18 a phase failed or was refused (setup, login, hire, bind, enter, start, no `until`, stall, ceiling, interrupt, `lease lost`). 19 the walk ran and was torn down but a wipe or a boss engagement happened, or a hire was still listed as online. A practice that stopped before its cycle budget (`practice stopped: max time`, `3 failed resets`, `4 attempts`, a stall) uses 18. 23 a fault verdict failed or a cleanup left a bot frozen (at least 23, even over 18/19). 15 the lease was refused (including slot 3). 14 teardown failed. 26 the instance ledger is at the cap. 29 the placement failed every try in the same instance. 2 usage.
